# RoamWeave

> 把零散的旅行想法整理成经过研究、现实可行、路线清晰、可以分享和继续修改的行程。

RoamWeave 是一个旅行规划项目。当前阶段先聚焦第一个能力：`travel-planner`。它的目标不是替用户直接预订机票、酒店或门票，而是先把目的地、约束、偏好、事实、假设和路线逻辑组织成一个可解释、可验证、可迭代的旅行计划。

English README: [README.md](./README.md)

## 产品方向

```text
Discover → Plan → Refine → Present → Search → Book
```

MVP 只覆盖 **Discover + Plan + Refine + 基础验证与呈现**。

后续的 Search 和 Book 可以接入航班、酒店、门票、交通和预订平台，但这些能力依赖实时价格、库存、时刻表、取消政策和平台数据。它们应该在规划模型稳定之后再加入。

## 核心原则

RoamWeave 的第一原则是：

> 先规划体验，再搜索库存。

旅行规划不应该一开始就被平台库存、广告位或单个酒店位置牵引。`travel-planner` 应该先回答：

- 这次旅行真正适合做什么？
- 每天应该围绕哪个区域或目标展开？
- 哪些地点必须保留，哪些应该删除、顺延或作为备选？
- 路线是否现实，是否过密，是否反复折返？
- 哪些事实需要核验，哪些只是推荐判断？

## MVP 能力范围

`travel-planner` 的第一版应该支持：

- 提取旅行硬约束和软偏好；
- 区分已确认事实、假设和待确认问题；
- 建立目的地简报；
- 按地理区域和旅行节奏组织地点；
- 为每天指定一个主要区域或目标；
- 控制行程密度、交通时间和不必要折返；
- 记录被删除、顺延或降级为备选的地点，并说明原因；
- 提供附近餐饮候选，而不是默认让餐厅主导路线；
- 提供天气、体力、拥挤或延误情况下的替代方案；
- 输出结构化行程数据和可读 Markdown 行程；
- 支持人工修改后的重新评估和验证。

## 输入

规划器应该能处理不完整、零散的信息，例如：

- 目的地或候选目的地；
- 日期、天数、抵达和离开时间；
- 出发地、机场、车站或住宿位置；
- 旅行人数、年龄、儿童、老人、无障碍需求或行李限制；
- 必去地点、明确排除地点和兴趣偏好；
- 节奏偏好、步行承受度和交通偏好；
- 预算范围和餐饮偏好；
- 已经预订或基本确定的航班、酒店、门票信息；
- 后续版本中的截图或旅行笔记。

缺失信息不应该被静默编造，而应该进入假设或待确认问题。

## 输出

MVP 的基础输出包括：

- 目的地简报；
- 结构化行程数据；
- Markdown 行程；
- 每日路线摘要；
- 已确认、可选、删除或顺延地点列表；
- 关键假设和未解决问题；
- 验证报告。

HTML 或交互式地图可以作为后续能力加入，但不应该早于核心规划契约和数据模型。

## 非目标

第一阶段不做：

- 自动预订机票、酒店、餐厅或门票；
- 实时价格比较；
- 平台账号登录或浏览器自动化；
- 航司积分、信用卡权益或复杂退款策略优化；
- 依赖特定旅行平台或多个外部 API key；
- 生成看似精确但不现实的逐分钟行程；
- 完整 Web 应用；
- 自动部署公开网站。

## 下一步

下一阶段应该完成 `travel-planner` 的设计与契约：

- `skills/travel-planner/SKILL.md`
- 规划参考文件；
- canonical itinerary data model；
- `schemas/itinerary.schema.json`；
- destination brief 和 itinerary Markdown 模板；
- 至少两个现实 fixtures；
- 可重复执行的验证清单。

在这些基础稳定之前，不应扩展到实时搜索、预订或外部集成。
